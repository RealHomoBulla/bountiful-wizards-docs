# Bonsai 2 27B локально — поставлено, измерено, вывод неутешительный

Поставлено 20.09 по его просьбе. Здесь только то, что **измерено на этой машине**, без обещаний.

## Что стоит и где лежит

| | |
|---|---|
| движок | `~/Bonsai-demo` — форк llama.cpp от PrismML, бинарники **`bin/vulkan/`** |
| модель | `/var/mnt/SamsungSSD/llm/bonsai2/Ternary-Bonsai-2-27B-PTQ1_0.gguf` (5,95 ГБ) |
| рядом | `…-PQ2_0.gguf` (7,21 ГБ, в 8 ГБ VRAM не влезает) и `…-mmproj-Q8_0.gguf` (601 МБ, зрение) |

🔑 **Движок намеренно оставлен в домашней папке, а веса — на SSD.** SSD смонтирован как **ntfs3**
(`/var/mnt/SamsungSSD`), а на NTFS теряется бит исполняемости — `llama-server` оттуда просто не
запустился бы. Веса читаются последовательно, им NTFS безразличен.

## Как запустить (сервер не висит постоянно — и не должен)

```bash
cd ~/Bonsai-demo && setsid env MANGOHUD=0 ./bin/vulkan/llama-server \
  -m /var/mnt/SamsungSSD/llm/bonsai2/Ternary-Bonsai-2-27B-PTQ1_0.gguf \
  --no-mmap -ngl 99 -fa on -c 8192 --host 127.0.0.1 --port 8080 &
curl -s http://127.0.0.1:8080/health      # {"status":"ok"}
```
API — OpenAI-совместимый: `http://127.0.0.1:8080/v1/chat/completions`.

⚠️ **`--no-mmap` обязателен.** Без него сервер падает с **SIGSEGV прямо на загрузке** (проверено:
штатный `start_llama_server.sh` → `EXIT=139`). Причина — mmap файла с ntfs3.
⚠️ **Сервер занимает 7,9 ГБ из 8 ГБ VRAM.** Пока он поднят, играть нельзя — карте нечем рисовать.
Поэтому он и не оставлен в автозапуске.

## Замеры — три прогона, одно число

| конфигурация | скорость |
|---|---|
| Vulkan, `-ngl 99`, ctx 8192 | **3,8 tok/s** |
| Vulkan, ctx 2048, `-ub 256` | **3,8 tok/s** (поджатие не дало ничего) |
| CPU-only (`-ngl 0`) | ~2,6 tok/s |

Модель действительно на карте — VRAM занято 7,92 ГБ, это не фолбэк на процессор.

🪦 **Моя оценка «15–25 tok/s» перед установкой оказалась неверной, и вот почему.** Я считал по
пропускной способности памяти (280 ГБ/с ÷ 6 ГБ ≈ 45 tok/s потолок, минус эффективность). Ошибка в
том, что у PrismML **быстрые тернарные ядра написаны под CUDA и Metal**; в `libggml-vulkan.so`
поддержка формата есть (295 упоминаний `PTQ1_0`/`PQ2_0` в бинарнике — проверял), но это путь
совместимости, а не оптимизированный. На RDNA2 он даёт примерно в пять раз меньше расчётного.

## Вывод про воркера в Orca: НЕ ГОДИТСЯ, и это не вопрос настройки

Две живые задачи, обе отвечены **правильно**:
1. «ore 7 / block 3 — сколько процентов блоков» → `30`. Верно.
2. Разбор фрагмента конфига депозита → ушло 500 токенов, 129 с.

**Проблема не в качестве, а в арифметике времени.** Это *думающая* модель (на базе Qwen3): ответ
сначала пишется в reasoning-канал, и простой вопрос стоит 84 токена, то есть ~30 секунд. Типичная
задача нашего воркера — десятки тысяч токенов; на 3,8 tok/s это **часы**, тогда как Command Code
делает то же за минуту. Как воркер в волне она бессмысленна.

**Где она всё же полезна:** одиночные приватные вопросы без сети, когда время не важно и не хочется
жечь лимиты. Для этого сервер и поднимается вручную на пару минут.

**Что могло бы изменить вывод:** младшая модель того же семейства — но их не существует,
опубликован только 27B (проверено по API HuggingFace: 8B/4B/1.7B у `Ternary-Bonsai-2` нет).
Остаются две ветки, обе непроверенные: ROCm-сборка вместо Vulkan (на Navi 23 это лотерея) или
другая модель в обычном формате под Vulkan, где ядра зрелые.
